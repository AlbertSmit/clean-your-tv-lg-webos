## Problems in the current PR

1. **Packaged script missing.** `root-edition/build.py:SERVICE_FILES` does not
   include `apply-toggles.sh`; the PR does not change the builder. Saving a
   setting cannot establish that enforcement code shipped or ran.
2. **Wrong lifecycle trigger.** Module-load `applyToggles()` is service start,
   not TV wake. No power subscription, wake hook or standby reconciliation is
   added. Opening settings or restarting the service can trigger another run.
3. **Fixed delay without cancellation.** Every settings change schedules a
   background reset if enabled. Switching it off does not cancel an existing
   sleeping process; multiple changes can overlap.
4. **Unvalidated state.** Missing/unknown `eArcSupport` becomes an empty string:
   the shell chooses `on`, then attempts to restore the empty value. Failed
   reads/writes are not checked. A process interruption between writes can
   leave the TV's preference altered.
5. **Unrelated effects.** Once the shared file exists, an absent/false Bluetooth
   flag powers Bluetooth on and an absent/false microphone flag unmutes it.
   Changing only eARC therefore changes unrelated user settings.
6. **Success means only saved.** `setToggle` ignores application errors and
   immediately returns success. The UI silently handles some read failures and
   does not distinguish saved configuration, running work, rejected calls and
   verified settings restoration.
7. **Private storage and lifecycle absent.** A new shared
   `/media/developer/natxo/settings.json` does not follow the Root runtime's
   private-state ownership conventions or document uninstall/update behavior.

## Separate the three symptoms

| Observed problem | Proposed operation | What it cannot prove |
| --- | --- | --- |
| Configured HDMI route has fallen back to TV speakers | Explicitly restore the validated configured route, with bounded retries | That audio is audible |
| HDMI remains selected but starts silent or late | Optional eARC protocol restart | That an already healthy connection needed it |
| Volume slider ineffective or numeric level wrong | Separate relative-volume/capability work | That the eARC link is broken |

The protocol service in upstream itself says healthy and desynchronized links
look identical through its observations. Do not infer silence from zero volume,
mute, `external_arc`, a negotiated codec, or `returnValue:true`. A muted film,
paused player or quiet scene must not initiate recovery.

## Options and recommendation

**A. Fixed delayed reset as in #27.** Small, but misses wake, interrupts working
audio and does not establish faster acquisition. Do not merge as the solution.

**B. Manual recovery plus opt-in boot/wake recovery (recommended).** Give users
a controlled way to test protocol restart; make automatic recovery experimental,
off by default, and available only with supported power observations. Treat
route fallback as a separate operation and cause. Measure before promoting.

**C. Permanent route watchdog.** Useful for installations deliberately pinning
one output, but broader than this report and can fight user choices or WOW
Orchestra. Do not add it in the initial eARC change.

### Proposed backend contract

- Root-only typed endpoints: `audioRecoveryStatus`,
  `setAudioRecoveryEnabled({enabled:boolean})`, and
  `recoverAudio({operation:"restart-earc"|"restore-hdmi"})`. Reject unknown keys,
  strings masquerading as booleans and unavailable operations. No arbitrary
  Luna URI, settings category, file path or shell command inputs.
- A small feature-owned worker independent of the Home UI and Home-button
  controller, installed only through owned installer registrations. Do not put
  a permanent watcher inside the existing emergency/recovery handler or assume
  that an ordinary JS service survives between RPCs.
- Read power and audio state through bounded, validated Luna calls; explicitly
  check LS2 permissions on the supported firmware. Prefer a supported tvpower
  subscription, deduplicate initial snapshots/duplicate Active notifications,
  and reconnect with bounded backoff. A service reconnect is not a new wake.
  Use a fresh bounded startup observation window on a confirmed cold boot.
  If wake detection cannot be established, expose manual recovery only.
  Never use wall-clock gaps alone as proof of wake.
- On enable, save the policy without immediately resetting working audio.
  After a genuine wake, schedule at most one reset after a settling interval;
  initially trial 10 seconds, with a 30-second eligibility window. These are
  experimental parameters to measure against the original 15-second approach,
  not compatibility claims. Late receiver readiness outside the window leaves
  a manual action, not an endless reset loop.
- Before protocol restart, require confirmed Active power, current and
  configured pure `external_arc`, and recognized `eArcSupport:"on"`. Skip
  ARC-only/off, unknown values, optical, Bluetooth, TV speakers, combined
  outputs and WOW Orchestra. Never temporarily enable eARC for an ARC-only
  setup. Automatic route restoration is out of initial scope.
- For manual route restoration, require an unambiguous configured pure HDMI
  preference; set that exact validated route. A missing preference is an error,
  never an excuse to default to `external_arc`. Do not normalize all `_harmony`
  suffixes into a different mode. Other routes can be supported later with
  separate evidence.
- Serialize all recovery requests with a worker/process-wide lock. Use a
  cancellation generation for disable, standby, output/user-setting changes,
  update and removal. Cancel queued work before its first settings write.
- Protocol restart is a transaction: privately record the original `on` value
  and transaction identity before writing `off`; verify the write; wait about
  2 seconds; restore `on`; verify restoration. Every call has a deadline. If a
  write times out, reconcile by reading before issuing another write.
- Restoration is cleanup even after cancellation. Track observable external
  setting changes and do not overwrite a newer user choice. The API offers no
  proven compare-and-swap: an interrupted transaction with ambiguous ownership
  must stop automatic work and request explicit restoration rather than blindly
  replaying its saved setting. Explain this limitation in device acceptance.
- On update/removal, stop scheduling, drain/reconcile an owned active transaction,
  remove only owned registrations, and retain an unresolved receipt for recovery.
  Keep the policy off after a failsafe/emergency stop until explicitly enabled.
- Private state under `/var/lib/clean-your-tv-root/audio-recovery/`, root-owned,
  restrictive modes, bounded schema, atomic writes and existing secure file
  conventions. No migration of unrelated `natxo` flags. No new network endpoint.
- Return operation phase, supported capabilities, skipped/error reason and
  settings-restoration result separately from the saved enabled flag. Report
  `completed-settings-restored`, not `sound-fixed`. Keep a bounded local event
  history with reason/duration/error code; no network addresses or app inventory.

### Proposed interface

One new row in the existing Root settings: **HDMI sound →**. Open a focused
subpanel using the same visual styling as the firmware panel, rather than adding
three global switches to the main card.

Suggested Russian copy:

> **Звук по HDMI**
>
> Выход: HDMI ARC/eARC · eARC включён
>
> **[Переподключить eARC]**
>
> Если звук не появился или появляется с задержкой. Звук может ненадолго
> прерваться.
>
> **Восстанавливать после включения** [выкл.]
>
> Экспериментально. Выполняет переподключение после включения ТВ и выхода
> из ожидания, даже если звук уже работает.
>
> Последняя попытка: настройка eARC восстановлена. Проверьте звук.
>
> [Назад]

Show **Вернуть звук на HDMI** only when a validated configured HDMI route has
actually fallen back; it replaces the main action for that state. Display ARC
versus eARC only from recognized settings, otherwise say the mode is unknown.
For ARC-only or WOW Orchestra, explain why protocol restart is unavailable;
do not imply that these modes are broken. If power observation is unsupported,
disable the automatic option with a reason while preserving supported manual
operations. Read failures show unavailable state and retry, never “off”.

During a transaction show “Переподключаем…” and reject duplicate actions;
Back can close the panel while the worker safely finishes cleanup. Restore
focus to the HDMI row on return, retain visible D-pad focus, announce results
through `aria-live`, and distinguish disabled controls from saved-off controls.
No volume slider or AV-sync delay slider belongs to this feature.

## Verification and acceptance before shipping

Implementation must cover package contents, worker installation/ownership and
removal, typed payloads, missing/invalid settings, LS2 denial/timeouts, overlapping
requests, canceled timers, duplicate wake events, clock jumps, service reconnect,
standby during a transaction, process death between writes, concurrent user
changes and emergency-stop behavior. Use fake Luna/power events and a controllable
clock; mock success is not evidence of audible recovery.

Run `npm ci`, `scripts/test.sh`, compatibility/build checks for changed components,
inspect the actual IPK/support archives and perform the applicable update/rollback
checks. Maintain all twelve localized guides and affected Root translations when
user-facing controls are implemented. Keep the implementation PR targeted at
`release/next`; do not select a version or claim publication during preparation.

Device acceptance must first reproduce the reporter's NANO95/Q950A behavior:
measure time to audible sound with identical content and receiver state, feature
off versus on, separately for cold boot and standby, Quick Start+ on/off where
available, and warm/cold receiver. Use at least five repetitions per compared
condition and record the spread and interruptions. A slower result is not a fix.
Check normal working audio, manual speaker switching, ARC-only, WOW Orchestra,
disconnected/late receiver, disable during waiting/recovery, rollback/removal and
triple-Home emergency release separately. No physical TV was tested here.
